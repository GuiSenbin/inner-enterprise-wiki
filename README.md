# 合晟资产内部 Wiki 智能问答系统

这是一个面向企业内部项目文档的 LLM Wiki / RAG 问答系统。项目以合晟资产内部数字化项目资料为样本，把 Markdown 原始文档、Wiki 概念词条和 Wiki 实体词条统一构建为本地知识库，通过 `FAISS` 向量检索和 `NetworkX` 双链图谱做混合召回，再调用通义千问大模型生成严格基于参考资料的中文回答。

项目优先跑通企业 Wiki/RAG 的核心闭环：

```text
原始文档 -> Markdown 双链词条 -> 文档切块 -> Embedding 向量化 -> FAISS 索引
       -> 图谱关系构建 -> 混合检索与重排 -> Prompt 组装 -> LLM 回答 -> 页面证据链展示
```

### 当前版本 2.0

当前版本已经完成从 Wiki 原型到可验证 RAG 问答闭环的升级：系统可以处理本地文档、构建向量索引、建立双链图谱、执行混合检索、对复杂问题进行综合重排，并在页面展示回答依据。

1. 系统内置 **12 个内部数字化项目**，每个项目固定包含需求规格、技术方案、项目管理计划、系统测试报告和内部验收报告，总计 60 份 Raw 文档。
2. 文档集经过缩减和规范化，避免早期版本中文件过多、来源分散、回答质量不方便人工核对的问题。
3. `Wiki/concept/` 和 `Wiki/entity/` 分别沉淀概念词条与实体词条，Raw 文档通过 `[[双链]]` 关联项目、部门、人员、技术组件和业务概念。
4. 索引构建阶段会扫描 Raw/Wiki 文档，按固定窗口切块，并调用 DashScope `text-embedding-v3` 生成向量写入 FAISS。
5. 检索阶段同时使用语义相似度和 Wiki 双链图谱：先用向量召回候选切片，再根据用户问题命中的图谱节点补充关联文档。
6. 重排阶段会综合向量分数、图谱命中和文档日期权重，让复杂问题更容易命中真正相关的资料。
7. 生成阶段会把 Top 5 检索切片组装进 Prompt，并要求模型严格基于参考信息回答；资料不足时不能编造。
8. 页面展示最终回答、当前问题、命中关键词、关联文档、完整 Prompt、Top 5 检索切片、综合分、语义分和图谱命中状态，方便检查“找得准不准、答得对不对”。
9. 后端提供模型白名单、请求大小限制、跨站重建保护、Embedding 降级提示和 LLM 回退状态，保证演示时能看清异常来源。
10. 测试覆盖知识库一致性、Raw/Wiki 双链完整性、HTTP API 契约、前端展示边界和核心文件语法。

💗 亮点：当前版本不是只做一个聊天页面，而是跑通了 **文档治理 -> 切块向量化 -> 语义召回 -> 图谱增强 -> 混合重排 -> 证据引用 -> 基于资料回答 -> 页面可解释展示** 的完整企业知识库问答路径，适合作为讲解 RAG 检索质量、可解释性和工程化边界的项目。

## 核心功能

### 1. 文档治理与知识库构建

项目把资料拆成三层：

- `Raw/`：保存原始项目文档，是回答事实源。
- `Wiki/concept/`：沉淀可复用概念，例如 RAG、来源引用、权限矩阵、回归测试、审计日志。
- `Wiki/entity/`：沉淀公司、部门、项目、人员、技术组件和业务模块。

Raw 文档中的 `[[双链]]` 会被解析为图谱关系，帮助系统不仅能按语义相似度找内容，也能按实体关系找到关联项目资料。

### 2. 切块与向量化

`WikiEngine.build_index()` 会扫描 Raw/Wiki 文档，把长 Markdown 按固定窗口切成带重叠的文本块：

- 短文档保持单块，减少无意义拆分。
- 长文档按 2000 字窗口和 300 字 overlap 切分，尽量保留上下文连续性。
- 每个切片保留文档名、文件名、类别、正文和双链 mentions，方便后续展示来源。

切块后系统调用 DashScope `text-embedding-v3` 生成向量，并写入本地 FAISS 索引。

### 3. 混合检索与重排

用户输入问题后，系统会执行两路召回：

1. **向量召回**：把问题向量化后，从 FAISS 中取语义相似的候选切片。
2. **图谱召回**：从用户问题里匹配 Wiki 节点，再沿 `NetworkX` 图谱找到关联 Raw 文档。

重排时会综合：

- 向量相似度分数。
- 是否命中图谱关联文档。
- 文档日期权重。

这样可以处理更复杂的问题，例如跨系统对比、权限/审计/监管留痕综合分析，不只依赖单次向量相似度。

### 4. 答案生成与引用校验

系统会把 Top 5 检索切片组装为“已知参考信息”，再交给通义千问生成回答。Prompt 明确要求：

- 必须严格基于参考资料回答。
- 参考资料没有提到时要说明不知道。
- 禁止使用外部知识和编造事实。

页面会同步展示 Prompt、来源文档和检索切片，方便人工检查答案是否真的来自资料，而不是模型自由发挥。

### 5. 原生 Web 可解释页面

V1 使用 Streamlit 快速搭建 Wiki 页面，但展示效果和证据链可读性不够理想。V2 改为 Python 标准库 HTTP 服务 + 原生 HTML/CSS/JavaScript 页面，页面职责更清晰：

- 左侧展示索引状态、文本切片数、图谱节点数和重建索引入口。
- 主区域展示问题输入、模型选择、最终回答和运行提示。
- 证据轨道展示 Top 5 检索切片、来源文档、分数和双链信息。
- Prompt 可以展开查看，便于解释 RAG 是如何把资料交给模型的。

## 版本说明

### V1：内部 Wiki 原型版 ✅

目的：先验证“企业文档能不能做成一个可查询的内部 Wiki”。

1. 把企业项目资料整理成可查询内容。
2. 使用 Streamlit 快速做出页面，方便输入问题和查看回答。
3. 早期文件数量较多，覆盖面广，但不方便快速判断回答质量。
4. 页面展示更像通用问答工具，证据链、来源、检索过程和回答质量不够直观。
5. 这一版验证了方向可行，但还没有把“RAG 为什么找得准、答案为什么可信”讲清楚。

💗 亮点：V1 跑通了内部文档问答的雏形，证明企业资料可以被整理成 Wiki 问答系统。

### V2：可验证 RAG 问答闭环版 ✅

目的：把早期 Wiki 原型升级为能讲清检索过程、回答来源和质量验证的企业级 RAG MVP。

1. 将文档集缩减并规范为 12 个项目、5 类文档、60 份 Raw 资料，方便人工核对和演示。
2. 建立 Raw / Concept / Entity 三层知识结构，让原始资料和知识词条职责分开。
3. 通过 Markdown 双链构建 Wiki 图谱，保留项目、部门、人员、技术组件和业务概念之间的关系。
4. 使用固定窗口和 overlap 切块策略，保留检索上下文。
5. 使用 DashScope Embedding + FAISS 构建本地向量索引。
6. 使用语义召回 + 图谱召回 + 综合重排，提升复杂问题的资料命中能力。
7. 使用严格基于参考信息的 Prompt 控制模型回答，降低幻觉。
8. 前端展示问题、答案、Prompt、来源文档、图谱命中、检索切片和分数，支持回答质量检查。
9. 增加知识库完整性测试、服务 API 测试和前端契约测试，保证项目内容和展示边界可验证。

💗 亮点：V2 的重点不是堆更多页面功能，而是把 **文档如何处理、资料如何找到、复杂问题如何重排、答案如何验证** 这条 RAG 主链路讲清楚。

### V3：大规模知识库与检索质量优化规划

目的：面向“如果文档越来越多怎么办、文件怎么越找越准、还能继续优化什么”这些深入问题，继续把 V2 的闭环升级成更接近真实企业知识库的系统。

1. **文档太多怎么办**：支持增量索引、按项目/部门/时间/文档类型建立元数据过滤，避免每次全量重建。
2. **切块怎么更合理**：从固定窗口升级为按标题、表格、章节和语义边界切块，减少重要信息被截断。
3. **怎么越找越准**：增加 BM25 关键词召回、向量召回、图谱召回、多路召回融合和 Cross-Encoder / LLM rerank。
4. **复杂问题怎么处理**：增加 query rewrite、问题拆解和多跳检索，让对比类、归纳类、跨项目问题先拆成多个检索子任务。
5. **答案怎么更可信**：把回答拆成结论和引用来源，要求每个关键结论能对应到具体文档切片。
6. **怎么评估检索质量**：建立固定评估问题集，记录期望命中文档、Top K 命中率、引用准确率和人工评分。
7. **真实企业怎么落地**：增加权限过滤、数据脱敏、访问审计、部门隔离和密级标记，避免用户检索到无权限资料。
8. **性能和成本怎么控制**：缓存热门问题、缓存 Embedding、异步建库、批量向量化，并按文档变化范围局部更新索引。

💗 亮点：V3 不是推翻 V2，而是在 V2 已经跑通的 RAG 闭环上继续研究规模、准确率、可信度、权限和成本。

## 技术架构

- 后端服务：Python 标准库 `ThreadingHTTPServer`
- 前端页面：原生 HTML、CSS、JavaScript
- 向量索引：FAISS
- 图谱关系：NetworkX
- Embedding：DashScope `text-embedding-v3`
- 大模型：通义千问 OpenAI 兼容接口，默认 `qwen-plus-2025-07-28`
- 配置管理：`.env` + `src/config.py`
- 本地知识库：Markdown Raw 文档 + Wiki 概念词条 + Wiki 实体词条
- 测试框架：unittest

## 目录结构

| 路径 | 作用 |
| --- | --- |
| `server.py` | Python 标准库 HTTP 服务入口，提供静态页面、状态接口、问答接口和索引重建接口 |
| `src/wiki_engine.py` | 核心问答引擎，负责文档扫描、切块、向量化、索引构建、混合检索、重排和生成 |
| `src/config.py` | 模型白名单、默认模型、Top K 和请求大小限制 |
| `web/` | 原生前端页面，负责输入、状态、答案、Prompt 和证据链展示 |
| `Raw/` | 60 份合晟资产内部项目 Markdown 原始文档 |
| `Wiki/index.md` | 知识库总览，维护项目范围、文档类型、概念和实体入口 |
| `Wiki/concept/` | 概念词条库 |
| `Wiki/entity/` | 实体词条库 |
| `data/wiki_index/` | 本地索引产物目录，重建索引后生成 |
| `scripts/regenerate_hesheng_kb.py` | 合晟资产示例知识库生成脚本 |
| `tests/` | 知识库完整性、服务 API 和前端契约测试 |
| `docs/constitution.md` | 项目开发和维护规则 |

## 本地启动

### 1. 准备环境

建议使用：

- Python 3.11+
- DashScope API Key

### 2. 安装依赖

```bash
pip install -r requirements.txt
```

### 3. 配置 Key

在项目根目录创建 `.env`：

```bash
DASHSCOPE_API_KEY=你的 DashScope API Key
```

`.env` 不应该提交到仓库。

### 4. 启动服务

```bash
python server.py
```

访问：

```text
http://127.0.0.1:8000
```

如果 `data/wiki_index/` 为空，请在页面左侧点击“重建本地索引”。重建索引会调用 Embedding 接口。

### 5. 常用命令

```bash
# 运行全部测试
python -m unittest discover tests

# 运行知识库一致性测试
python -m unittest tests.test_hesheng_kb_integrity -v

# 运行服务 API 测试
python -m unittest tests.test_server_api -v

# 检查核心 Python 文件语法
python -m py_compile server.py src/wiki_engine.py scripts/regenerate_hesheng_kb.py
```

## 开发约定

- Raw 文档是事实源，新增回答依据必须能追溯到 Raw 或 Wiki 词条。
- 新增 Raw 文档时，文件名保持 `合晟资产_项目名称_文档类型_YYYYMMDD.md`。
- 新增概念或实体时，要保证 Raw 双链可以解析到对应词条。
- 修改检索策略时，要同步检查页面证据链是否还能展示来源、分数和命中原因。
- 修改模型、Top K、请求限制等配置时，优先集中到 `src/config.py`。
- 修改核心流程后至少运行 `python -m unittest discover tests`。
- 真实 API Key 只能放在 `.env`，不要提交到仓库。
