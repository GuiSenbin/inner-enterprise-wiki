# 合晟资产知识编译型 LLM Wiki 项目宪法

本文档是本项目的最高级工程规范，约束后续前端、后端、知识库、数据脚本、测试、配置和项目文档。所有改动都必须服务于同一目标：建设一个可查询、可追溯、可解释、可扩展、可验证的知识编译型企业级 LLM Wiki 系统。

## 一、不可破坏的核心原则

1. **Raw 是事实源**：`Raw/` 保存原始业务资料，回答和 Wiki 沉淀必须能追溯到事实来源。
2. **Wiki 是知识层**：`Wiki/concept/` 和 `Wiki/entity/` 负责沉淀概念、实体和目录，不只是原始文档切片附件。
3. **知识先被编译**：Raw/Wiki 文档必须先编译为 `DocumentChunk`、`WikiNode`、`LinkGraph`、`RetrievalCandidate` 和 `AnswerEvidence` 等中间件，再被问答链路消费。
4. **RAG 是底层能力**：向量召回、关键词召回和图谱召回服务于 LLM Wiki，不应把系统退回成单纯 RAG 演示。
5. **查询必须有证据**：后端不能只返回答案，还要返回来源、切片、图谱命中、关键词命中、分数、意图、策略、重排依据、证据状态和降级状态。
6. **证据不足必须拒答**：领域外、无证据或低置信问题应返回明确兜底说明，不为了“有回答”而调用大模型编造内容。
7. **前端只做展示**：页面可以替换，但不能实现检索、重排、Prompt 组装、模型调用或知识编译逻辑。
8. **变更必须可验证**：修改代码、数据、脚本或文档后，要运行对应测试；无法运行时必须说明原因和风险。

## 二、系统分层边界

| 层级 | 责任 | 不允许做的事 |
| --- | --- | --- |
| 知识库层 | 维护 Raw、Concept、Entity 和 `Wiki/index.md` | 混入无关公司、无来源结论、占位文本 |
| 知识编译层 | 扫描文档、解析双链、识别文档类型、生成切片和图谱 | 调用大模型生成答案 |
| 索引层 | 构建和加载 FAISS、BM25、本地图谱索引 | 直接拼 Prompt 或处理前端状态 |
| 意图路由层 | 判断问题类型、匹配 Wiki 节点、选择检索策略 | 执行真实检索或修改知识库 |
| 检索层 | 合并向量、关键词和图谱候选证据 | 判断最终答案是否可信 |
| 重排层 | 计算综合分和排序原因 | 调用大模型 rerank，除非新增明确模块和测试 |
| 回答层 | 判断证据状态、估算置信度、组装 Prompt、调用模型或拒答 | 扫描文件、构建索引、实现页面逻辑 |
| 服务层 | 校验请求、托管静态文件、透传 API 响应 | 硬编码业务检索规则 |
| 前端层 | 展示输入、状态、答案、Prompt、证据和运行提示 | 实现 FAISS、BM25、rerank 或 Prompt 生成 |

`WikiEngine` 必须保持门面类定位，只负责协调各层模块；当文件继续膨胀时，应优先下沉职责，而不是把新逻辑继续塞回门面。

## 三、目录职责

| 目录 / 文件 | 职责 | 规范 |
| --- | --- | --- |
| `Raw/` | 原始业务文档 | 文件名使用 `合晟资产_项目名称_文档类型_YYYYMMDD.md`；关键实体和概念使用 `[[双链]]` |
| `Wiki/index.md` | 知识库总目录 | 维护项目范围、文档类型、项目列表、核心概念和实体索引 |
| `Wiki/concept/` | 概念词条 | 解释“是什么、用于什么场景、关联哪些资料” |
| `Wiki/entity/` | 实体词条 | 描述“是谁/是什么、属于哪个业务范围、关联哪些文档” |
| `src/models.py` | 共享数据结构 | 新增跨层数据必须先定义清楚字段含义 |
| `src/knowledge_loader.py` | 文档加载和双链解析 | 不直接调用检索或模型 |
| `src/chunker.py` | 文档切块 | 切块策略变化必须补测试 |
| `src/graph_builder.py` | 双链图谱构建 | 图谱节点和边类型必须可解释 |
| `src/vector_store.py` | Embedding 和 FAISS | 模型名、维度、批大小必须从 `src/config.py` 读取 |
| `src/bm25_store.py` | 关键词索引 | 保持本地可测试，不依赖外部服务 |
| `src/query_router.py` | 轻量意图识别 | 新增意图必须补典型问题测试 |
| `src/retriever.py` | 多路召回合并 | 保留召回来源标记 |
| `src/reranker.py` | 轻量重排 | 每个加权原因都要能进入 `rerank_reasons` |
| `src/answer_service.py` | 证据判断、Prompt 和模型调用 | 必须支持拒答和模型 fallback |
| `server.py` | HTTP 服务入口 | 只做请求校验、静态托管和调用门面 |
| `web/` | 展示层 | 必须展示答案、证据、意图、策略、置信度和异常提示 |
| `tests/` | 自动化验证 | 覆盖知识库、编译、检索、重排、API 和前端契约 |

## 四、API 响应契约

`/api/answer` 成功响应必须至少包含以下字段：

- `query`
- `answer`
- `prompt`
- `intent_type`
- `retrieval_strategy`
- `rerank_explanation`
- `evidence_status`
- `confidence_score`
- `confidence_label`
- `matched_nodes`
- `related_docs`
- `retrieved_results`
- `used_model`
- `embedding_failed`
- `llm_failed`

`retrieved_results` 中每条证据必须至少包含：

- `chunk.doc_name`
- `chunk.category`
- `chunk.text`
- `chunk.mentions`
- `score`
- `vector_score`
- `keyword_score`
- `graph_hit`
- `keyword_hit`
- `direct_match_score`
- `rerank_reasons`

新增字段时应向后兼容；删除或改名字段必须同步修改前端和测试。

## 五、知识库规范

1. Raw 文档必须保持同一企业背景，不能混入无关公司、无关行业或旧数据残留。
2. Raw 中出现的 `[[词条]]` 必须能在 Wiki 词条或 Raw 文档中找到对应目标。
3. 每个项目资料应保持文档类型完整，当前标准为需求规格、技术方案、项目管理计划、系统测试报告和内部验收报告。
4. 新增项目资料后，要同步维护 Raw、Wiki、索引和测试。
5. 概念词条不能只写标题，必须说明概念含义、适用场景和关联资料。
6. 实体词条必须能解释该实体和业务范围的关系。
7. 禁止新增无来源结论、临时占位文本、重复脏句和没有业务含义的内容。

## 六、检索质量规范

1. 向量召回用于语义相似，不能单独承担所有问题。
2. BM25 用于编号、指标、字段、百分比、专有名词和短语精确匹配。
3. 图谱召回用于实体、概念和 Raw 文档之间的关系扩展。
4. 重排必须保留可解释原因，不能只返回一个黑盒分数。
5. 文档类型加权必须和问题意图一致，例如验收问题优先验收报告，技术问题优先技术方案。
6. 直接事实命中适用于数字、比例、编号和完整短语，不应泛化成无约束加分。
7. 证据置信度是检索证据质量评分，不是大模型自评。
8. 低置信问题必须允许拒答，不能为了页面好看而强行生成。

## 七、前端规范

1. 前端只做展示和交互，不实现检索、重排、Prompt 组装和模型调用。
2. 页面必须展示最终回答和证据链，至少包括用户问题、来源文档、检索切片、图谱命中、关键词命中、问题意图、检索策略、重排依据、证据置信度和异常提示。
3. 页面应提供调试入口查看完整 Prompt 或核心检索上下文。
4. 页面文案必须体现企业内部知识查询，不写成通用聊天机器人。
5. 替换前端时，先稳定后端接口或返回结构，再改 UI。
6. 推荐问题必须服务于验证检索能力，例如数字事实、实体画像、项目风险、验收指标和跨系统对比。

## 八、配置与模型规范

1. 生成模型、模型白名单、fallback 顺序、Embedding 模型、Embedding 维度、批大小、Top K 和请求大小限制必须集中在 `src/config.py`。
2. 业务模块不得硬编码模型名、Embedding 维度或 Top K。
3. API Key 只能放在 `.env` 或本地私密配置中。
4. `.env`、本地索引、缓存产物和 `__pycache__` 不提交仓库。
5. 更换 Embedding 模型时必须确认维度、索引文件和测试是否同步。
6. 未来接入真实企业数据时，必须增加数据脱敏、权限过滤、访问审计和密级标记。

## 九、代码注释规范

注释只解决三件事：说明文件边界、解释核心流程、提示容易误改的逻辑。禁止用注释重复代码字面含义。

### 1. 文件头说明

Python、JavaScript、Shell 等脚本类文件必须有文件头；HTML、CSS、JSON、YAML 等声明式文件在结构复杂或承担关键配置时，也要在顶部或相邻文档中说明用途。

Python 文件头使用：

```python
"""
定位：所属层级或模块。
职责：当前文件负责的核心能力。
依赖：关键外部接口、目录、模块或运行环境。
"""
```

JavaScript / TypeScript 文件头使用：

```javascript
/*
定位：所属层级或模块。
职责：当前文件负责的核心能力。
依赖：关键接口、DOM 节点、模块或运行环境。
*/
```

### 2. 函数和类注释

必须写函数/类说明：对外入口函数、核心业务类、读写文件函数、网络请求函数、模型调用函数、索引构建函数、知识库修改函数、承担外部依赖隔离作用的测试假对象。

可以不写函数/类说明：很短的格式化函数、无副作用且命名清楚的 helper、含义直观的测试用例方法。

### 3. 行内注释

只在容易误解或容易改错的逻辑前写行内注释，例如双链解析、图谱构建、混合重排、模型回退、拒答逻辑、路径安全检查和前端证据链渲染。

禁止写这类注释：

```python
# 定义变量
count = 0

# 遍历列表
for item in items:
    ...
```

## 十、测试规范

常用验证命令：

```bash
python -m unittest discover tests
python -m unittest tests.test_hesheng_kb_integrity -v
python -m unittest tests.test_knowledge_compilation -v
python -m unittest tests.test_server_api tests.test_frontend_contract -v
python -m py_compile server.py src/*.py scripts/regenerate_hesheng_kb.py
```

必须重点验证：

1. Raw 文档命名、日期、类型和企业背景。
2. 双链是否存在断链。
3. 核心实体和概念是否存在。
4. 概念词条是否被 Raw 实际使用。
5. 切片策略是否符合预期。
6. 意图识别是否能覆盖典型问题。
7. BM25 是否能命中编号、字段、指标和数字事实。
8. 重排原因是否进入 API 和前端证据轨道。
9. 领域外、无证据和低置信问题是否拒答。
10. 模型配置是否仍从 `src/config.py` 读取。
11. 服务 API 和前端展示契约是否同步。

## 十一、变更检查清单

提交或阶段性交付前检查：

1. 是否破坏前端、后端、知识库、脚本、测试的职责边界。
2. 是否保留答案来源、意图、策略、置信度和证据链。
3. 是否新增无来源内容、占位文本或脏数据。
4. 是否补充必要文件头、docstring 和复杂逻辑注释。
5. 是否运行对应测试，或明确说明未运行原因。
6. 是否保持 README、Wiki index、测试和实际项目内容一致。
7. 是否避免把 V3 已经完成的能力写成未来规划，或把未来规划写成当前能力。
