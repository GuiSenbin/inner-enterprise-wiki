# 合晟资产企业级 LLM Wiki 项目宪法

本文档是本项目的最高级工程规范，约束后续前端、后端、知识库、数据脚本、测试、配置和项目文档。所有改动都必须服务于同一目标：建设一个可查询、可追溯、可解释、可扩展、可验证的企业级 LLM Wiki 系统。

## 一、核心原则

1. **Raw 是事实源**：`Raw/` 保存原始业务资料，回答和 Wiki 沉淀必须能追溯到事实来源。
2. **Wiki 是知识层**：`Wiki/` 负责沉淀概念、实体和目录，不只是原始文档切片。
3. **查询必须有证据**：后端不能只返回答案，还要返回来源、切片、图谱命中、分数和降级状态。
4. **页面可以替换**：展示层可替换为不同前端，但不能把核心查询逻辑写进页面。
5. **变更必须可验证**：修改代码、数据、脚本或文档后，要运行对应测试或说明未验证原因。

## 二、目录职责

| 目录 / 文件 | 职责 | 规范 |
| --- | --- | --- |
| `Raw/` | 原始业务文档 | 文件名使用 `合晟资产_项目名称_文档类型_YYYYMMDD.md`；关键实体和概念使用 `[[双链]]` |
| `Wiki/index.md` | 知识库总目录 | 维护项目范围、文档类型、项目列表、核心概念和实体索引 |
| `Wiki/concept/` | 概念词条 | 解释可复用业务或技术概念，避免孤立词条 |
| `Wiki/entity/` | 实体词条 | 描述公司、部门、项目、人员、技术组件和业务模块 |
| `src/` | 后端查询引擎 | 负责建库、检索、重排、Prompt、模型调用和降级处理 |
| `server.py` | 服务入口 | 提供静态页面、状态接口、问答接口和索引重建接口 |
| `web/` / 未来前端 | 页面展示层 | 只负责输入、交互、状态和证据展示 |
| `scripts/` | 数据生成和维护脚本 | 批量生成、重建、修复知识库，运行后必须配套验证 |
| `tests/` | 自动化验证 | 覆盖知识库一致性、内容质量和代码可运行性 |

## 三、前端规范

1. 前端只做展示和交互，不实现检索、重排、Prompt 组装和模型调用。
2. 页面必须展示最终回答和证据链，至少包括用户问题、来源文档、检索切片、图谱命中、检索依据和异常提示。
3. 页面应提供调试入口查看完整 Prompt 或核心检索上下文。
4. 页面文案必须体现企业内部知识查询，不写成通用聊天机器人。
5. 替换前端时，先稳定后端接口或返回结构，再改 UI。

## 四、后端规范

1. 查询引擎必须独立于页面框架，不能依赖 Streamlit、Vue、React 等具体前端。
2. 后端核心返回结果必须包含：`answer`、`matched_nodes`、`related_docs`、`retrieved_results`、`used_model`、`embedding_failed`、`llm_failed`。
3. Prompt 必须要求模型基于参考信息回答；资料不足时不能编造。
4. Embedding、LLM、索引加载失败时，要有明确错误或降级状态。
5. 检索权重、Top K、切片大小、模型名和 Embedding 维度应逐步配置化。
6. 新增检索策略必须说明用途，例如实体关系召回、语义召回、关键词召回或重排增强。

## 五、知识库规范

1. Raw 文档必须保持同一企业背景，不能混入无关公司、无关行业或旧数据残留。
2. Raw 中出现的 `[[词条]]` 必须能在 Wiki 词条或 Raw 文档中找到对应目标。
3. 新增项目资料后，要同步维护 Raw、Wiki、索引和测试。
4. 概念词条解释“是什么、用于什么场景、关联哪些资料”。
5. 实体词条说明“是谁/是什么、属于哪个业务范围、关联哪些文档”。
6. 禁止新增无来源结论、临时占位文本和没有业务含义的内容。

## 六、脚本规范

1. 生成脚本必须可重复运行，避免同一输入生成不可解释差异。
2. 项目、部门、人员、技术组件、概念等基础数据应集中维护。
3. 脚本输出必须符合 Raw 命名、Wiki 双链和日期规则。
4. 脚本不能绕过测试批量修改知识库。
5. 自动生成内容必须服务于企业查询，不为了增加复杂度而堆概念。

## 七、代码注释规范

注释只解决三件事：说明文件边界、解释核心流程、提示容易误改的逻辑。禁止用注释重复代码字面含义。

### 1. 文件头说明

每个代码文件顶部必须说明文件职责。Python、JavaScript、Shell 等脚本类文件必须有文件头；HTML、CSS、JSON、YAML 等声明式文件在结构复杂或承担关键配置时，也要在顶部或相邻文档中说明用途。

文件头只保留三件事：这个文件在哪里、做什么、依赖什么。Python 文件头使用：

```python
"""
定位：所属层级或模块。
职责：当前文件负责的核心能力。
依赖：关键外部接口、目录、模块或运行环境。
"""
```

JavaScript / TypeScript 文件头使用：

```javascript
/*
定位：所属层级或模块。
职责：当前文件负责的核心能力。
依赖：关键接口、DOM 节点、模块或运行环境。
*/
```

填写要求：每项控制在 1 句话内；只写当前已实现能力；“依赖”只写关键协作对象，不列无关细节。

### 2. 函数和类注释

必须写函数/类说明：对外入口函数、核心业务类、读写文件函数、网络请求函数、模型调用函数、索引构建函数、知识库修改函数、承担外部依赖隔离作用的测试假对象。

可以不写函数/类说明：很短的格式化函数、无副作用且命名清楚的 helper、含义直观的测试用例方法。

函数/类说明只要求说清楚“做什么”和“关键依赖”。有参数、返回值、异常或降级逻辑时再补，不强制写成大型模板。

### 3. 行内注释

只在容易误解或容易改错的逻辑前写行内注释，例如双链解析、图谱构建、混合重排、模型回退、降级处理、静态文件路径安全检查、前端证据链渲染。

禁止写这类注释：

```python
# 定义变量
count = 0

# 遍历列表
for item in items:
    ...

# 返回结果
return result
```

### 4. 前端与配置文件注释

1. `web/app.js` 中的核心函数要用简短注释说明用途，尤其是 API 请求、答案渲染、证据渲染和错误提示。
2. `web/styles.css` 只给布局分区、状态样式和复杂响应式规则加注释，不逐条解释颜色和间距。
3. `web/index.html` 保持语义结构清楚，只有在结构不直观时才加注释。
4. 配置文件只注释非显而易见的配置项，例如模型、密钥读取、服务端口、检索权重和构建参数。
5. Markdown 文档不是代码注释对象，但项目规范、接口说明和知识库说明必须保持清晰可追溯。

## 八、测试规范

常用验证命令：

```bash
python -m unittest tests.test_hesheng_kb_integrity -v
python -m unittest tests.test_server_api -v
python -m py_compile server.py src/wiki_engine.py scripts/regenerate_hesheng_kb.py
```

必须重点验证：

1. Raw 文档命名、日期、类型和企业背景。
2. 双链是否存在断链。
3. 核心实体和概念是否存在。
4. 概念词条是否被 Raw 实际使用。
5. 代码是否通过语法检查。
6. 后续新增检索策略时，要补固定问题和期望来源的评估用例。

## 九、配置与安全规范

1. API Key 只能放在 `.env` 或本地私密配置中。
2. `.env`、本地索引和缓存产物不提交仓库。
3. 未来接入真实企业数据时，必须增加数据脱敏、权限过滤、访问审计和密级标记。
4. 配置项不能散落在页面和业务逻辑中，应逐步集中管理。

## 十、变更检查清单

提交前检查：

1. 是否破坏前端、后端、知识库、脚本、测试的职责边界。
2. 是否保留答案来源和证据链。
3. 是否新增无来源内容、占位文本或脏数据。
4. 是否补充必要文件头、docstring 和复杂逻辑注释。
5. 是否运行对应测试，或明确说明未运行原因。
6. 是否保持 README、Wiki index、测试和实际项目内容一致。
